Recorded so they aren't re-audited next run. Each was verified real (except
where noted). Ask the advisor to `plan <#>` to turn any into a plan.

  script alias for `php .github/validate-skills.php` and no CONTRIBUTING, so
  contributors learn of bad frontmatter only when CI fails. Fix: add a
  `"validate-skills"` composer script + a README/CONTRIBUTING line. *Natural

  `.gitattributes`.

## Direction options (not planned — design/spike candidates)

Forward-looking; each grounded in repo evidence. Ask the advisor for a spike
plan (`/improve plan D<n>`) on any of these.

- **D1 — `github-issue-create` skill.** GitHub Issues has only the tail-end
  `github-issue-updates`, while Jira has a full create/rework/updates trio. A
  `github-issue-create` mirroring `jira-create`, gated on the existing
  `github-issues` tag, closes the asymmetry. *HIGH-grounded, S–M.*
- **D2 — Catalog self-authoring loop.** `ai-guidelines` documents the *consumer*
  layout (`.ai/skills/`), never this catalog's `resources/boost/` + README
  tables + `.boost-tags.yaml` + schema — which is *why* #1's drifts happen. A
  catalog-authoring checklist (enforced by 002's invariant check) is the
  root-cause fix. *HIGH-grounded, M. Pairs with 002.*
- **D3 — Formalize the hihaho upstream-adoption pipeline.** History is dominated
  by manual batch adoption (`adopt-hihaho-upstream-2026-06`); an adoption ledger
  + scripted upstream-diff makes the main growth engine auditable. *MED–HIGH, M–L.*
- **D4 — Tracker parity (Linear/generic).** The tag + `mcp.*` slot machinery is
  already tracker-agnostic, making a third tracker cheap — but in-repo demand is
  inferred, not evidenced. *MED (weakest); pursue only if it matches the actual
  workflow.*
